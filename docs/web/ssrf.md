# Server Side Request Forgery

Server Side Request Forgery (SSRF) occurs when an application makes a server-side request using attacker-controlled input without sufficiently restricting where that request can go.

Instead of the attacker's browser directly accessing the destination, the vulnerable application performs the request.

This can potentially expose services and resources that are accessible to the application server but not directly accessible to the tester.

!!! warning "Authorised Security Testing"
    Perform SSRF testing only against applications and systems for which you have explicit authorisation. Be particularly careful with internal services, cloud metadata services and other infrastructure that may fall outside the agreed assessment scope.

---

## Objectives

The primary objectives of SSRF testing are to determine:

- whether user-controlled input causes a server-side request
- which protocols are accepted
- which hosts can be reached
- whether internal addresses are accessible
- whether localhost is accessible
- whether redirects are followed
- whether DNS resolution can influence the destination
- whether URL validation is performed safely
- whether blind SSRF exists
- whether cloud metadata services could be exposed
- whether application credentials are automatically attached to requests
- what security impact can be demonstrated safely

A useful mental model is:

```text
Attacker
   ↓
Application Input
   ↓
Server
   ↓
Server-Side HTTP Client
   ↓
Destination
```

The security boundary changes because the request originates from the application environment rather than from the attacker's machine.

# Blind SSRF

Blind SSRF occurs when the application performs the server-side request but does not return the response to the tester.

Example:

```text
Input
 ↓
Application
 ↓
Server-Side Request
 ↓
Remote Service
```

while the application returns only:

```text
Request processed
```

The response from the remote service is not visible.

---

## Blind SSRF Workflow

```text
Identify URL Input
       ↓
Insert Controlled Callback
       ↓
Send Request
       ↓
Application Responds Normally
       ↓
Monitor Collaborator / Interactsh
       ↓
Interaction Received?
       ↓
Correlate
       ↓
Reproduce
```

Blind SSRF can still be security relevant even when response content is unavailable.

# DNS Interaction vs HTTP Interaction

Different callbacks reveal different things.

A DNS interaction indicates:

```text
Application
     ↓
DNS Resolver
     ↓
Attacker-Controlled Domain
```

An HTTP interaction provides stronger evidence that the application proceeded beyond DNS resolution and attempted a network request.

Therefore:

```text
DNS Only
   ↓
Interesting

DNS + HTTP
   ↓
Stronger Evidence
```

Interpret callbacks carefully.

# URL Parsing

URL validation is difficult because multiple components may interpret a URL differently.

The processing chain may look like:

```text
User Input
     ↓
Application Validator
     ↓
URL Parser
     ↓
DNS Resolver
     ↓
HTTP Client
     ↓
Destination
```

If these components interpret the URL differently, validation may not protect the actual request.

---

# URL Components

A URL can contain several components:

```text
scheme://userinfo@host:port/path?query#fragment
```

For example:

```text
https://user@example.com:443/path?x=1#section
```

When reviewing SSRF defences, determine which component is actually being validated.

---

# Userinfo Confusion

URLs can contain user information before the host:

```text
https://username@example.com/
```

This can create parsing confusion in poorly implemented validation logic.

Different parsers must agree on:

```text
Scheme
Host
Port
Path
```

Security controls should use a well-tested URL parser rather than custom string matching.

---

# Host Validation

Weak validation might attempt checks such as:

```text
URL contains trusted.example
```

or:

```text
URL starts with https://trusted.example
```

String comparisons can be dangerous when used as URL security boundaries.

Instead:

```text
Parse URL
   ↓
Extract Host
   ↓
Normalise
   ↓
Resolve
   ↓
Validate Destination
   ↓
Connect
```

---

# Allowlist Testing

Some applications restrict destinations to approved hosts.

For example:

```text
https://api.example.com
```

Determine whether the restriction applies to:

```text
Scheme
Hostname
Port
Resolved IP
Redirect destination
```

A secure implementation should validate the actual destination, not merely the original string.

---

# Redirect Based SSRF

An application may validate the initial URL but then follow redirects.

Example:

```text
Application
     ↓
https://allowed.example/redirect
     ↓
HTTP 302
     ↓
Different Destination
```

The important question is:

> Is the redirect destination validated as carefully as the original destination?

# Redirect Chains

Applications may follow multiple redirects.

Conceptually:

```text
URL A
 ↓
302
 ↓
URL B
 ↓
301
 ↓
URL C
```

Security validation should apply throughout the redirect chain.

Do not assume that validating only `URL A` is sufficient.

---

# DNS Resolution

Hostname validation can also become complicated because:

```text
Hostname
   ↓
DNS
   ↓
IP Address
```

Security decisions should consider the resolved address.

A hostname that appears external may resolve to an internal address.

---

# DNS Rebinding

DNS rebinding exploits differences between DNS resolution performed during validation and DNS resolution performed when the connection is made.

Conceptually:

```text
Validation
    ↓
DNS Answer A

Later Connection
    ↓
DNS Answer B
```

If the application validates only the first result, the final destination may differ.

Secure SSRF defences should account for DNS resolution changes and validate the actual address used for the connection.

---

# Alternative IP Representations

Different parsers and platforms may interpret IP addresses in different representations.

For defensive testing, investigate whether the application's URL validation consistently recognises local and private addresses after normalisation.

The key principle is:

```text
Parse
 ↓
Normalise
 ↓
Resolve
 ↓
Classify Address
 ↓
Connect
```

rather than maintaining a simple string blocklist.

---

# IPv6

Do not forget IPv6.

Localhost may be represented as:

```text
::1
```

Applications that block IPv4 loopback addresses but ignore IPv6 can still expose local services.

SSRF protections should consistently handle:

```text
IPv4
IPv6
IPv4-mapped IPv6
```

---

# Ports

SSRF may allow the attacker to influence the destination port.

Example:

```text
https://example.com:8443/
```

This can potentially expose services running on non-standard ports.

Determine whether the application restricts:

```text
Host
Port
Scheme
```

Do not perform broad internal port scanning unless explicitly authorised.

---

# Protocol Handling

Determine which URL schemes are supported.

Common expected schemes are:

```text
http
https
```

Applications should generally reject unnecessary protocols.

Depending on the underlying library, other schemes may exist.

The secure design principle is:

```text
Allow only required protocols
```

rather than attempting to block every dangerous protocol individually.

---

# File Scheme

Some libraries may understand:

```text
file://
```

If supported, this may cause the application to interact with local files rather than remote HTTP resources.

Whether this is possible depends entirely on:

```text
Programming language
Library
Framework
Configuration
URL handler
```

Do not assume support.

# Cloud Metadata Services

SSRF can be particularly serious in cloud environments because application workloads may have access to metadata services.

Cloud platforms use metadata endpoints to expose information to workloads.

Potential platforms include:



## Important Cloud Testing Consideration

Do not retrieve cloud credentials simply to prove SSRF.

A safer process is:

```text
Confirm SSRF
      ↓
Determine Cloud Environment
      ↓
Confirm Metadata Reachability if Authorised
      ↓
Retrieve Minimal Non-Sensitive Metadata
      ↓
Stop
```

If credentials or tokens could potentially be exposed, describe the impact without unnecessarily collecting them.

---

# AWS Metadata

AWS EC2 provides an Instance Metadata Service.

Modern environments can use:

```text
IMDSv2
```

which introduces session-oriented protections compared with older metadata access patterns.

When assessing AWS-hosted applications, determine:

```text
Is metadata reachable?
Is IMDSv2 required?
Can the vulnerable request mechanism satisfy the required interaction?
```

Do not assume that the presence of SSRF automatically means AWS credentials are retrievable.

---

# Azure Metadata

Microsoft Azure provides an Instance Metadata Service for virtual machines and other workloads.

Metadata access has specific request requirements.

When Azure is identified, the relevant security question is whether the vulnerable server-side request mechanism can satisfy those requirements.

Do not indiscriminately request sensitive identity tokens.

---

# Google Cloud Metadata

Google Cloud also exposes workload metadata through a metadata service.

Requests require platform-specific behaviour.

As with other cloud providers:

```text

```

does not automatically equal:


# SSRF vs Open Redirect

SSRF and open redirect can involve similar URL parameters but represent different behaviour.

Open redirect:

```text
User
 ↓
Application
 ↓
HTTP Redirect
 ↓
User's Browser Visits Destination
```

SSRF:

```text
User
 ↓
Application
 ↓
Server Makes Request
 ↓
Destination
```

Determine who actually makes the request.

---

# SSRF vs Client-Side Fetching

A browser-side request is not SSRF.

For example:

```javascript
fetch(userControlledUrl)
```

executed in the user's browser is client-side behaviour.

SSRF requires:

```text
Server-Side Request
```

Trace the actual request origin.

---

# SSRF vs XXE

XXE can sometimes produce SSRF-like network interactions.

For example:

```text
XML Parser
   ↓
External Entity
   ↓
Network Request
```

The root vulnerability in that situation may be XXE rather than generic URL-fetching SSRF.

Document the actual vulnerable component and root cause.

---

# SSRF vs Command Injection

A URL parameter passed to:

```bash
curl USER_INPUT
```

could potentially involve both SSRF and command injection depending on how the command is constructed.

Determine the actual sink:

```text
HTTP Client
```

versus:

```text
Shell
```

This is why source-to-sink analysis matters.

```text
Connection timed out
Name resolution failed
Invalid URL
Unsupported protocol
Certificate validation error
Too many redirects
Connection reset
```

These errors may reveal how the backend request is processed.

Do not expose such verbose network errors to normal application users.

---

# WAF Behaviour

A WAF may block obvious SSRF test strings.

Indicators include:

```text
403
406
Generic security page
Connection termination
Parameter-specific blocking
```

Separate:

```text
WAF Behaviour
```

from:

```text
Application SSRF Protection
```

A WAF blocking `127.0.0.1` does not prove the application itself securely validates destinations.

---

# False Positives

Potential false positives include:

```text
Client-side requests
Browser prefetching
Security scanners

DNS resolvers
Monitoring systems
Email security scanners
URL preview services
WAF processing
```

Correlate:

```text
Unique identifier
Timestamp
Source
Request path
HTTP headers
```

before concluding that SSRF exists.

# Validation

A strong SSRF finding should establish:

```text
SOURCE
  ↓
Attacker-Controlled URL
  ↓
Server-Side Request
  ↓
Destination
  ↓

  ↓
Security Impact
```

For example:

```text
webhook_url
     ↓
Webhook Test Function
     ↓
Backend HTTP Client
     ↓
Controlled Collaborator Domain
     ↓
DNS + HTTP Interaction
```

# Example Finding Structure

```text
Title
Server Side Request Forgery in Webhook Test Function

Affected Endpoint
POST /api/webhooks/test

Affected Parameter
url

Authentication Required
Yes

Description
The application performs a server-side HTTP request to a
user-controlled URL without sufficiently restricting the
destination.

Testing confirmed that the backend server performed HTTP and
DNS requests to a controlled external domain.

Impact
An attacker with access to the affected functionality may be
able to cause the application server to communicate with
destinations that are not normally accessible to the attacker.

Depending on network configuration, this could expose internal
services or other trusted resources.

Recommendation
Restrict outbound requests to explicitly approved destinations,
validate the resolved destination address, revalidate redirect
targets and prevent access to loopback, private, link-local and
other non-public network ranges unless explicitly required.
```

# Remediation

SSRF protection should use multiple controls.

A strong design may include:

```text
Strict destination allowlist
      ↓
Parse URL
      ↓
Allow required schemes only
      ↓
Validate hostname
      ↓
Resolve hostname
      ↓
Validate resolved IP
      ↓
Connect
      ↓
Validate redirects
```

Additional protections include:

```text
Outbound firewall rules
Network segmentation
Restricted service accounts
Cloud metadata protections
Request timeouts
Response size limits
Restricted ports
DNS controls
Monitoring
```

---

# Prefer Allowlists

If the application only needs to communicate with specific services, use an explicit allowlist.

Example:

```text
api.partner.example
images.examplecdn.com
```

Avoid accepting arbitrary destinations if the business function does not require them.

---

# Validate Resolved Addresses

Do not validate only the hostname string.

Conceptually:

```text
URL
 ↓
Parse Hostname
 ↓
DNS Resolution
 ↓
IP Address
 ↓
Address Classification
 ↓
Allow / Deny
```

Block access to network ranges that the functionality does not require.

---

# Revalidate Redirects

If redirects are supported:

```text
Initial URL
    ↓
Validate
    ↓
Request
    ↓
Redirect
    ↓
Validate New Destination
    ↓
Follow
```

Do not blindly follow redirects after validating only the original URL.

---

# Restrict Protocols

If only web resources are required, allow:

```text
https
```

and, where genuinely required:

```text
http
```

Reject unnecessary protocols.

---

# Restrict Ports

If the application only requires standard web services, consider restricting destination ports.

For example:

```text
443
```

or:

```text
80
443
```

depending on business requirements.

---

# Network Level Controls

Application validation should be supported by network controls.

For example:

```text
Application
     ↓
Egress Firewall
     ↓
Approved Destinations
```

The application should not have unrestricted outbound access if it does not require it.

---

# Cloud Metadata Protection

Cloud environments should use the provider's current metadata protections.

Examples include:

```text
Modern metadata authentication requirements
Network restrictions
Workload identity controls
Least privilege
```

Do not rely solely on application-level URL filtering to protect cloud credentials.

- [ ] Check HTTP interaction

- [ ] Avoid broad internal scanning
- [ ] Determine whether private ranges are blocked
- [ ] Determine whether link-local destinations are blocked

- [ ] Distinguish DNS from HTTP
- [ ] Reproduce callback

- [ ] Collaborator
- [ ] Intruder where useful

- [ ] Review redirect handling
- [ ] Review protocol restrictions
- [ ] Review port restrictions

- [ ] Confirm server-side request
- [ ] Confirm affected parameter
- [ ] Confirm repeatability
- [ ] Exclude browser-side behaviour
- [ ] Exclude scanner-generated callbacks
- [ ] Determine actual reachable destinations
- [ ] Collect minimal evidence
- [ ] Stop after sufficient proof
